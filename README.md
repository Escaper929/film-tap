# film-tap

碰一下贴在机身上的 NFC 挂件，就知道这台相机里装的是什么胶卷、装了多久、还剩几张。

**这个仓库不是网站，它是一个容器镜像的源。** 页面和数据都由你 NAS 上的一个进程
（[nas/server.py](nas/server.py)）发出来，镜像由 GitHub Actions 自动构建，
NAS 上由 watchtower 自动更新。仓库里没有任何一行属于你的数据。

**容器没在跑，网址就打不开** —— 页面没有离线缓存，数据也只有 NAS 上那一份。
这不是限制，是有意的：以前版本靠浏览器缓存做到「后端挂了也能打开」，结果就是
容器停了、反代明明在报 502，页面却照样显示得好好的，把「服务挂了」这件事藏了起来。

## 它解决什么

胶片一卷能拍很久，几台机身轮着用的时候，很容易忘记某台机器里装的是什么卷、
什么时候装的、还剩几张没拍完。这个 App 把「机身 ↔ 当前胶卷」的状态记下来，
靠一个挂在背带上的 NFC 挂件直达：

- 挂件里写一条 URL 记录：`https://<你的域名>:<端口>/?c=<机身ID>`
- 手机碰一下 → 直接打开那台机身 → 看到当前卷、装了多少天、还剩几张
- 换卷只改 App 里的数据，**标签一辈子只写一次**

## 功能

- **机身管理** —— 名称、品牌、型号、画幅（135 / 120 / 110 / 大画幅）
- **机内胶卷** —— 装卷、张数、回卷自动归档
- **胶卷库存** —— 手上还有哪些卷、各几卷、什么时候到期；装卷时自动扣
- **推拉提示** —— 填了实拍 EI 自动算推拉档位，送冲扫时提醒你交代店家
- **装卷天数** —— 超过 180 天标「该冲了」，超过 365 天亮红
- **拍摄历史 / 统计** —— 每台机身拍过的卷、常用胶卷 Top 5
- **冲扫备注** —— 一键复制成能直接发给冲扫店的说明
- **备份** —— 数据存自己 NAS 上；另有 WebDAV 与 JSON 导出导入两条退路

> **这里不数快门。** 机身计数器上本来就能看到拍了多少张，在手机里再记一遍
> 只会多一个要维护、还大概率记错的地方。App 只记「这卷是什么、多少张、装了多少天」。

## 部署

```bash
NAS_HOST=<你的 NAS 地址> NAS_USER=<SSH 用户> SSH_PORT=<SSH 端口> ./nas/deploy.sh
```

脚本做的事：拉镜像 → 建 `<部署根>/data` → 起容器（**只挂 data 卷**）→ 可选设一次密码。
**自动更新默认不开**，装哪条见下面「怎么更新」。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `NAS_HOST` | 必填 | NAS 地址（也可以写 `~/.ssh/config` 里的 Host 名） |
| `NAS_USER` / `SSH_PORT` | 当前用户 / 空 | SSH。`SSH_PORT` 留空就让 ssh 自己定（先看 `~/.ssh/config`，否则 22）—— NAS 的 SSH 端口不是 22 的话，在 `~/.ssh/config` 里配一次，之后就不用每次传 |
| `BASE` | `/vol1/@appdata/film-tap` | 部署根，只用来放 `data/` |
| `PORT` | `8300` | 对外端口（容器内部固定 8300，这里只映射） |
| `UID_GID` | `1000:1001` | 容器以哪个身份跑，让数据文件归你而不是 root |
| `IMAGE` | `docker.io/liritian/film-tap:latest` | 换标签就能固定版本 |
| `FT_PASSWORD` | 空 | 只在首次初始化密码时用 |
| `VAULT_DIR` | 空 | **放着清单笔记的那一层目录**（默认是 `50_Assets`，不是 vault 根）；设了才挂到 `/vault` 并打开「从 Obsidian 同步」 |
| `VAULT_FILE` | `胶卷库存清单.md` | 笔记在 `VAULT_DIR` 里的相对路径 |
| `WATCHTOWER` | `no` | `yes` 才装**常驻** watchtower（要长期交出 docker.sock）。默认不装，自动更新走 `nas/watchtower-cron.sh` |

首次设一次密码（以后改密码是同一条命令，也可以不设 `FT_PASSWORD` 手动跑）：

```bash
ssh -p <SSH 端口> -t <SSH 用户>@<你的 NAS 地址> \
  'docker exec -it film-tap python3 /app/server.py --set-password'
```

反代加一条：域名 → `http://127.0.0.1:8300`（按域名分流，TLS 一张泛域名证书即可）。

### 怎么更新

三条路，按「省心」和「交出去多少」权衡。前两条用的都是**一次性** watchtower
（`--run-once`，跑完就退），docker socket 只在那一小段运行期间暴露。

```bash
# ① 现在手动更新一次（不装任何常驻容器）
NAS_HOST=<你的 NAS 地址> ./nas/update.sh

# ② 装每日自动更新：往 NAS 放一支脚本 + 一条 cron（推荐）
NAS_HOST=<你的 NAS 地址> NAS_USER=<SSH 用户> ./nas/watchtower-cron.sh
```

③ 想要最及时，就在部署时显式 `WATCHTOWER=yes` —— 起一个**常驻** watchtower，
按 `WATCHTOWER_INTERVAL` 查一次。代价是那个容器 24 小时挂着 `/var/run/docker.sock`。

> ⚠️ **watchtower 挂 `/var/run/docker.sock`，等于把 NAS 的 Docker 控制权交给它。**
> 三条路都用 `--label-enable` 把它限制在自己打了标签的容器上，不会碰 NAS 上别的容器。
> 另外注意自动更新意味着**升级时机不由你决定**；数据在 `data` 卷里，
> 回滚就是换个标签再起一次（`IMAGE=docker.io/liritian/film-tap:sha-xxxxxxx`）。

> ⚠️ **Docker Hub 连不上时 watchtower 会静默跳过** —— 退出码 0、容器不动、什么都不报。
> 所以 `nas/filmtap-update.sh` 结尾特意把「容器在用的镜像」和「镜像名现在指向的」
> 两个 ID 打出来对比，不一致就是这次没更成。走 ② 的话日志在 NAS 的 `~/.filmtap-update.log`。

### 镜像怎么来的

```
push 到 main / 打 v* 标签
   → GitHub Actions：① node _selftest.js → ② 构建 → ③ 拿真镜像起容器冒烟 → ④ 推 Docker Hub
   → NAS 上更新：cron 每天跑一次一次性 watchtower（或常驻 watchtower / 手动 update.sh）
```

推的是 **Docker Hub 而不是 GHCR**，理由只有一个字：拉得到。`ghcr.io` 在国内经常拉不动，
而 watchtower 无人值守 —— 拉不到它不报错，只会停在旧镜像上，看起来「配好了」其实从没成功。
需要在仓库放两个 secret：`DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`（Personal access token，
权限 Read & Write），少任何一个 CI 会在登录那步失败。

三道门是有意的顺序：① 自检不过就**不构建**（视图渲染、数据流、凭据护栏、以及
「没有离线缓存」那条都在里面）；② 构建之后**再拿真镜像起容器**走一遍探活 → 设密码 →
登录 → 存 → 读 → 未登录 401（光看「构建成功」证明不了 `COPY` 没漏文件）；③ `latest`
要等冒烟过了才指过去，否则坏镜像会被下一次自动更新拉下来。标签：`latest` 跟 main，
`sha-<短哈希>` 每个提交一个。

## 怎么用

只有一个地址：`https://<你的域名>:<端口>/?c=<机身ID>`。
`#/settings` 页的「已登记的机身 ID」会列出每台机身的完整 URL，直接复制即可。

打开页面先过一道入口：**连不上服务端就进不去**（容器没跑、反代没起来、
地址不对，都会停在一张说明页上，而不是拿本机旧数据糊弄你）。连上了、这台设备
还没登录，就输一次密码 —— 登录态是服务器下发的 cookie，之后这台设备就记住了。
设置页还有「载入示例数据」可以先看成品（`?demo=1` 则不连服务端直接看示例）。

**一次性准备（每台机身做一次）** —— 推荐「先写卡，再碰一下登记」，
这样机身 ID 由你自己定，好记也好念：

1. **挑一个短 ID** —— 小写字母数字，别重复：`m6` / `fm2` / `rollei35`
2. **写标签** —— 用 NFC Tools 写入一条 **URL** 记录：`https://<你的域名>:<端口>/?c=m6`。
   必须是 URI 记录且放**第一条**：iOS 后台读取只认 URI 记录，多条时只用第一条，
   也不支持自定义 scheme
3. **碰一下登记** —— 系统弹出通知 → 点开 → 页面显示「这个挂件还没登记」，
   填名称、品牌、型号、画幅 → 保存。以后碰这一下就直接落到这台机身
4. **打印挂件** —— `python model/build_fob.py` 出 `fob.stl`，层高 0.16mm，
   打完**第 17 层**（Z = 2.72mm）暂停放入标签，再封顶 2.24mm

**日常** —— 碰一下直接落在那一台机身：换一卷（张数按画幅预填，回卷自动归档）、
编辑这卷（填 ISO 与实拍 EI 出推拉提示）、一键复制冲扫备注、库存自动扣一卷。

本地预览：`python -m http.server 8080` 之后打开 `http://127.0.0.1:8080/?demo=1`。
**必须带 `?demo=1`** —— 不带的话页面会老老实实去找 `/api/health`，找不到就停在
「连不上服务端」那一屏（这是对的，不是坏了）。`?demo=1` 是唯一一条不连服务端的
渲染路径：灌一份示例数据、直接进应用，专门给截图和看排版用。
直接双击 `index.html` 只能看界面，同样得加 `?demo=1`。

## 数据与安全

**主路只有一条：你自己 NAS 上的一个目录。** 页面、接口、数据全在那一个容器里。

```
NFC 标签 → https://<你的域名>:<端口>/?c=m6
              │
     反代（终结 TLS，按域名分流）
              │
     http://127.0.0.1:8300              ← 只绑回环，不进局域网
              │
     film-tap 容器（nas/server.py，零第三方依赖）
       GET  /           页面（index.html / sw.js / manifest）
       POST /api/login  校验密码 → Set-Cookie（400 天）
       GET  /api/data   读数据          PUT /api/data  原子写 + 历史副本 + 版本号校验
              │
     <部署根>/data/                      ← 唯一的挂载卷，更新镜像时不动它
       data.json                       ← 数据本体，就是一个普通文件
       config.json                     ← 密码的加盐哈希（0600）
       sessions.json                   ← 会话表（0600）
       history/<时间戳>-<版本>.json      ← 每写一次留一份（保留 120 份）
```

| | 数据在哪 | 要配什么 | 本机被清空后 |
|---|---|---|---|
| **自建 NAS（默认形态）** | 你自己 NAS 上一个文件 | 一个密码 | **什么都不用做 —— 会话活着，打开就自动拉回来** |
| WebDAV（备用，默认不开） | 你自己的 NAS | 地址与账号，前面得有别的东西补 TLS + CORS | 重填同样的三样 → 手动点「从 NAS 恢复」 |
| 导出 JSON（保命） | 你选的地方 | 无 | 手工导入 |

⚠️ **只有自建那条能做到「什么都不做就自愈」。** 关键差别只有一处：
**登录态住在服务器下发的 cookie 里，而不是 `localStorage` 里。**
Safari 的 ITP 只清**脚本能写**的存储（`localStorage` / `IndexedDB` / Cache API /
`document.cookie`），服务器用 `Set-Cookie` 下发的 cookie（这里还带 `HttpOnly`，
脚本根本碰不到）不在清理范围内，有效期可以给到 400 天。于是本机被清掉之后，
会话还活着 → 打开页面自动把数据拉回来，不用重填任何东西。

> 证据到哪一步：机制是 Apple 的公开规则，端到端也**模拟验证过**（自检里钉住了这条链子），
> 但**没有真的等满 7 天**，那一段只能靠规则本身。
>
> 导出 JSON 那条不依赖任何凭据、也不依赖任何服务还活着 ——
> **它是唯一不会因为「你忘了什么」而失效的一条**，值得顺手做一次。

**刻意保持的几条：**

- **没有离线缓存，也没有 Service Worker。** 页面必须联网才能打开：容器停了、
  反代返回 502，浏览器就该拿到一个打不开的地址，而不是从自己的缓存里端出旧壳。
  页面还会主动把**以前装过的** SW 注销掉、缓存清空（`sw.js` 也换成了自毁版），
  否则老客户端会一直吃缓存里那份旧页面。本机 `localStorage` 只是服务端那份的
  **镜像**，启动时必须走完「探活 → 会话 → 拉数据」，任何一步不成都停在 gate 上，
  **绝不拿本机旧数据先顶上**。
- **后端只绑 `127.0.0.1`**，不进局域网，只有 NAS 本机的反代连得上。
- **密码只以 PBKDF2-SHA256 加盐哈希（20 万次）落在 `config.json`（0600）**，
  页面里、代码里、日志里都不出现明文。日志只记「方法 + 路径 + 状态码」，**绝不记请求体**。
- **写文件是「同目录临时文件 → fsync → `os.replace`」**，半截写入不会顶掉好的那份。
- **限速只认 `client_address[0]`，绝不读 `X-Forwarded-For`** —— XFF 客户端可随便写，
  用它分桶等于限速不存在（实测 20 次伪造 XFF 全绕过；改用 client_address 后 8 次即锁）。

### 两类会被直接拦下的上传（409）

- **「服务端有 N 台机身、送来的这份却是空的」** —— 会静默清空服务端，所以直接拒绝，
  提示先拉一次对齐。真实触发场景：本机存储被系统清理，或你换台新设备随手记了一台机身。
  真想清空走设置页的「清空全部数据」，那条路会明确问你。
- **版本号对不上** —— 客户端把「上次读到的内容哈希」一起发过去，对不上就回 409 让先拉一次。
  于是两台设备同时开自动同步时，「悄悄覆盖」变成了「被拦下并告诉你」。
  同步是**整库快照，后写的赢，没有合并**；真要两台一起用，建议只在一台开自动同步。

> ⚠️ 千万别把 NAS 地址或密码硬编码进源码。仓库是公开的，一旦提交，密码就永久留在
> Git 历史里 —— 删掉代码也没用，必须改密码 + 重写历史才能挽回。这条不是假设，这个项目真踩过。
> 同理，提交前把 noreply 邮箱设上（`git config --global user.email "<id>+<用户名>@users.noreply.github.com"`，
> 并在 GitHub → Settings → Emails 勾上 “Keep my email addresses private”），
> 文档里的示例路径一律写 `/path/to/...`。这几条 `_selftest.js` 都会拦。
>
> 部署地址（域名 + 端口）同理：别写进脚本或文档，要传就用参数或环境变量，
> 示例一律写 `https://<你的域名>/`。脚本里带默认地址，等于把部署位置写进公开仓库。

## 联到 Obsidian（可选）

如果你用 Obsidian 记胶卷库存，可以让 App 的库存跟着笔记走。设置页会多出
「从 Obsidian 同步胶卷库存」一块：一个按钮先预览、一个按钮真同步。

**三份笔记，分工是硬的：**

| 笔记 | 角色 |
|---|---|
| `胶卷账本.md` | **唯一真源**。`## 期初`（冻结快照）+ `## 流水`（只能追加）+ `## 历史`（旧记录，不参与累加） |
| `胶卷库存清单.md` | **生成物**。三列（品牌/型号、格式、数量），每次同步按账本重算；别手改 |
| `胶卷拍摄记录.md` | **日志，可选**。每次「拍完换卷」由 film-tap 追一行（相机 / 胶卷型号 / 装卷日 / 退卷日 / 张数 / 备注） |

公式只有一条：**库存 = 期初 + Σ流水**。`## 历史` 那一节**故意不参与求和** ——
那些事都发生在期初之前、已经含在期初里了，再加一遍就会把卷数算多。
所以要改库存，就往 `## 流水` 追加一行（购入 `+2` / 售出 `-1` / 消耗 `-1` / 盘点修正），
别去动期初或清单。

打开方式（vault 与 App 在同一台 NAS 上）：

```bash
NAS_HOST=<你的 NAS 地址> VAULT_DIR=/vol1/1000/ObsidianVault/obsidian/50_Assets ./nas/deploy.sh
```

`VAULT_DIR` 要指向**放着这几份笔记的那一层目录** —— 默认布局下是 `50_Assets`，
不是 vault 根（填 vault 根会找不到笔记）。它会以读写方式挂到容器内的 `/vault`，
两份文件名分别由 `VAULT_FILE`（默认 `胶卷库存清单.md`）与
`VAULT_LEDGER`（默认 `胶卷账本.md`）指定。**这两个都要能读到，少一个整块停用** ——
没账本就无从重算，没清单就没地方写。

拍摄记录由 `VAULT_SHOTS` 指定（默认 `胶卷拍摄记录.md`）。**它是可选的**：
设成空字符串就是关掉这一块，其余同步照常（预览里会写明「这块跳过了」）。
设了却读不到就直接报错，不会静悄悄地不记。

**只挂 `50_Assets` 这一层，不要挂整个 vault** —— 容器只拿到它需要的最小写权限。
`VAULT_DIR` 不设就整块停用，App 照常用。

**「拍完换卷」会自动追一行：** 在 App 里装新卷顶掉旧卷、或者点「标记为空机」，那一卷
都会进机身的 `history`。同步时后端把 history 里**已经退过卷**的条目补进拍摄记录。
张数写的是**标称张数**（36 / 12…）—— 实际拍了几张只有机身计数器知道，App 里早就不记了；
若这卷按 EI 推过（比如 ISO 400 推到 1600），备注里会带一句「按 EI 1600 拍」。
去重靠两条：**基线里的自然键**（机身 id + 型号 + 两个日期）和**行内容的指纹**
（指纹里不含机身名，所以给机身改个名不会把老记录重写一遍）。

**App 装卷会自己记进账本：** 同步时后端拿 App 的库存和基线比，变少的追加一条
「消耗」流水（日期取机身里那卷的 `loadedAt`，不是同步那天），变多的追加「盘点修正」。
这些自动行的备注以 `[自动]` 开头 —— 必须能和手写的行分开，否则算不出
「账本这一侧自己变了多少」。追加量是 `F - L` 这种**幂等**的式子：重放一次算出来就是 0，
所以哪怕基线还没写成就崩了，也不会重复扣减。

⚠️ **几件先知道的事：**

- **只有手动触发**，没有定时任务 —— 想同步就点一下。
- **别让别的同步插件把刚落地的改动盖回去。** 笔记如果是 remotely-save / WebDAV
  多端同步的，刚同步完就在**另一台设备**上让插件做一次全量覆盖，可能拿旧副本冲掉
  刚才的回写。稳妥做法：同步完在这台设备上先让插件把本地版本推上去。
- **容器得对 vault 有写权限。** `UID_GID`（默认 `1000:1001`）要跟 vault 目录的属主一致，
  否则回写会失败（返回 409，笔记不动）。
- **两条护栏，都只拒绝、一个字节不碰：** ① `## 流水` 的行数不到上次的一半
  （文件像被写坏了）；② **`## 期初` 的哈希变了** —— 它是冻结快照，被改过就说明
  有人在动不该动的东西。
- **回写只替换数量那一格里的数字**（款式有增减时才整段重建那张表），
  写之前把原文备份到 `data/obsidian-backups/`（保留 20 份）。

## iPhone 上的两条硬规则

> 这两条**只对 iPhone 成立**。Android 上把 PWA 装到桌面反而是加分项 ——
> 「别装到主屏」是 iOS 的存储隔离逼出来的规矩，不是这个 App 的偏好。

**1. 碰标签只会打开 Safari，不会打开主屏 Web App。** iOS 的后台读卡只在链接是
**有效的 Apple Universal Link**（原生 App 声明 Associated Domains）时才交给 App。
我们是纯网页，所以 iOS 一律交给 Safari。推论：**不要「添加到主屏幕」** ——
主屏 Web App 的存储与 Safari **互相隔离**，碰标签进去的是 Safari 那份，
点主屏图标进去的是另一个存储空间。数据本身在 NAS 上不会因此丢，
但两边的登录态和本机镜像互相看不见，你会莫名其妙被要求再输一次密码 ——
没必要给自己找这个麻烦。

**2. Safari 里的数据闲置 7 天会被静默清空。** 防护从最省心往下排：
跑在自建后端上（**这一层不需要任何对策**，见上一节）→ 顺手导出 JSON 存 iCloud Drive
（唯一不依赖任何凭据和服务的保命路）→ 配 WebDAV 备份（重填地址账号再恢复）→
哪怕什么都不配，**每周打开一次**也能重置计时器（注意是从**最后一次交互**算起）。

## 自检

```bash
node _selftest.js      # 全部视图渲染 + 张数 / 装卷 / 库存与导入 / 改名迁移 / 凭据护栏 / 没有离线缓存
python _obsidian_test.py   # Obsidian 联动的账本解析 / 重算 / 追加流水 / 回写（零依赖，不用真 vault）
python _shots.py       # 需先起本地服务（截图走 ?demo=1，不连后端），截图输出到 shots/
FT_PASSWORD=<密码> python _firstrun.py https://<你的域名>/   # 打真实部署，走一遍「过 gate → 空库首次使用」（需 playwright）
```

> `_firstrun.py` 的部署地址**只能从参数或 `FT_URL` 环境变量进来**，脚本里不写死任何
> 地址 —— 仓库是公开的，写进去就等于把部署位置一起公开出去。不给地址会直接退出（码 2）。
> 后端设了密码就再给一个 `FT_PASSWORD`；不给而页面又停在登录那一屏时，脚本会说明
> 原因并以码 2 退出。

> `_selftest.js` 在内存里造数据 + 直接跳哈希，从不点按钮、不进表单，
> 所以「过登录 gate → 空库 → 登记第一台机身 → 装卷 → 刷新 → 数据还在」这条
> **每个新用户唯一会走的**路径由 `_firstrun.py` 用真浏览器补上。

### 没有离线缓存，也没有 SW 要同步

以前这里有一条硬规矩：改完 `index.html` 必须同步改 `sw.js`（把 shell 的 SHA-256
抄进 `SHELL_FP`、`CACHE` 版本号 +1），否则浏览器不会装新 SW，线上是新版、手机一直
停在旧版而且不报错。**现在整条规矩撤掉了** —— 没有缓存，也就没有要同步的东西。

现在反过来钉：`sw.js` 不许有任何缓存能力（不开 cache、不监听 fetch），但它必须会
**自毁**（清空所有 cache + 注销自己）。页面这边也不注册 SW，还会主动把已经装过的
旧 SW 注销掉、缓存清干净。两头都留着，是因为老客户端在服务端不可用时根本取不到
新的 `sw.js`，只能靠下一次「服务端正常时」访问来自毁脱钩。

`_selftest.js` 里的「没有离线缓存（容器停=打不开）」那条就是在钉这件事：谁哪天
把 `caches.open` 或 `addEventListener("fetch")` 加回来，自检立刻失败。

> 顺带一提，**页面本身也是 `no-cache, must-revalidate`**：浏览器每次都得回来问
> 服务端一次。否则「容器停了但页面还能从 HTTP 缓存里端出来」会以另一种形式复现。
