# film-tap

碰一下贴在机身上的 NFC 挂件，就知道这台相机里装的什么胶卷、装了多久、还剩几张。

**这个仓库不是网站，它是一个容器镜像的源。** 页面和数据都由你自己 NAS 上的一个进程
发出来（`nas/server.py`），镜像由 GitHub Actions 自动构建、
NAS 上由 watchtower 自动更新。仓库里没有任何一行属于你的数据。

## 它解决什么

胶片一卷能拍很久，几台机身轮着用的时候，很容易忘记某台机器里装的是什么卷、
什么时候装的、还剩几张没拍完。

这个 App 把「机身 ↔ 当前胶卷」的状态记下来，靠一个挂在背带上的 NFC 挂件直达：

- 挂件里写一条 URL 记录：`https://<你的域名>/?c=<机身ID>`
- 手机碰一下 → 直接打开那台机身 → 看到当前卷、装了多少天、还剩几张
- 换卷只改 App 里的数据，**标签一辈子只写一次**

## 功能

- **机身管理** —— 名称、品牌、型号、画幅（135 / 120 / 110 / 大画幅）
- **机内胶卷** —— 装卷、张数、回卷自动归档
- **胶卷库存** —— 手上还有哪些卷、各几卷、什么时候到期；装卷时自动扣
- **推拉提示** —— 填了实拍 EI 自动算推拉档位，送冲扫时提醒你交代店家
- **装卷天数** —— 超过 180 天标「该冲了」，超过 365 天亮红
- **拍摄历史** —— 每台机身拍过的卷、各用了多少天
- **统计** —— 机身数、已用胶卷数、常用胶卷 Top 5
- **冲扫备注** —— 一键复制成能直接发给冲扫店的说明
- **备份** —— 数据存自己 NAS 上；另有 WebDAV 与 JSON 导出导入两条退路

> **这里不数快门。** 机身计数器上本来就能看到拍了多少张，
> 在手机里再记一遍只会多一个要维护、还大概率记错的地方。
> App 只记「这卷是什么、多少张、装了多少天」。每卷多少张仍然保留
> （`135 · 36 张`），因为那是冲扫和归档时要用的信息，和「已拍几张」是两回事。

## 数据存哪儿

**主路只有一条：你自己的 NAS 上一个目录。** 页面、接口、数据全在那一个容器里。

```
NFC 标签 → https://<你的域名>/?c=m6
              │
     反代（终结 TLS，按域名分流）
              │
     http://127.0.0.1:8300              ← 只绑回环，不进局域网
              │
     ┌────────┴──────────┐
     │  film-tap 容器     │  GET  /           页面（index.html / sw.js / manifest）
     │  nas/server.py    │  POST /api/login  校验密码 → Set-Cookie（400 天）
     │  零第三方依赖       │  GET  /api/data   读数据
     └────────┬──────────┘  PUT  /api/data   原子写 + 历史副本 + 版本号校验
              │
     <部署根>/data/                       ← 唯一的挂载卷，更新镜像时不动它
       data.json                        ← 数据本体，就是一个普通文件
       config.json                      ← 密码的加盐哈希（0600）
       sessions.json                    ← 会话表（0600）
       history/<时间戳>-<版本>.json       ← 每写一次留一份，版本历史在这里
```

| | 数据在哪 | 要配什么 | 本机被清空后 |
|---|---|---|---|
| **自建 NAS（默认形态）** | **你自己 NAS 上一个文件** | **一个密码** | **什么都不用做 —— 会话活着，打开就自动拉回来** |
| WebDAV（备用，默认不开） | 你自己的 NAS | 地址与账号，**前面得有别的东西补 TLS + CORS** | 重填同样的三样 → 手动点「从 NAS 恢复」 |
| 导出 JSON（保命） | 你选的地方 | 无 | 手工导入 |

⚠️ **只有「自建 NAS」那条能做到「什么都不做就自愈」。**
关键差别只有一处：**登录态住在服务器下发的 cookie 里，而不是住在 `localStorage` 里。**

浏览器「闲置 7 天清空存储」清的是**脚本能写**的那些 —— `localStorage`、`IndexedDB`、
Cache API、`document.cookie`。服务器用 `Set-Cookie` 下发的 cookie（这里还带了
`HttpOnly`，脚本根本碰不到）**不在清理范围内**，有效期可以给到 400 天。
于是本机数据被清掉之后，会话还活着 → 打开页面自动把数据拉回来，**不需要重填任何东西**。

> 证据到哪一步，说清楚：机制是 Apple 的公开规则（ITP 只清理脚本可写存储），
> 端到端也**模拟验证过** —— 清掉 `localStorage`、保留 cookie、重新打开，
> 数据自己回来了（自检里也钉住了这条链子）。但**没有真的等满 7 天**，
> 那一段只能靠规则本身。

导出 JSON 那条不依赖任何凭据、也不依赖任何服务还活着 ——
**它是唯一不会因为「你忘了什么」而失效的一条**，值得顺手做一次。

> ⚠️ 千万别把 NAS 地址或密码硬编码进源码。仓库是公开的，一旦提交，
> 密码就永久留在 Git 历史里 —— 删掉代码也没用，必须改密码 + 重写历史才能挽回。
> 这条不是假设，这个项目真踩过。`_selftest.js` 里有护栏盯着，但它只能拦形状。

### 提交之前：把 noreply 邮箱设上（一次就够）

**Git 提交里的作者邮箱是公开的。** 不用克隆仓库，任何人敲

```bash
curl -s https://api.github.com/repos/Escaper929/film-tap/commits | grep email
```

就能拿到 —— 而且它**永久留在历史里**，删文件没用，只能重写历史。

所以别等到已经泄露了再去改历史，一开始就别用它提交：

```bash
git config --global user.email "60599586+Escaper929@users.noreply.github.com"
```

（`id+用户名@users.noreply.github.com`，在你的 GitHub → Settings → Emails
底下能直接复制。**顺手把那个页面上的 “Keep my email addresses private” 勾上**，
那是一条额外的保险，就算哪次忘了设也还有兜底。）

> ⚠️ 设一次是不够的：全局配置**不跟着仓库走**。换台机器克隆下来，
> 或者用另一套 Git（编辑器的内嵌 Git 常常是另一份 `gitconfig`），
> 那份上没有这个设置，提交又会带上真实邮箱。所以换环境之后
> 先敲一句 `git config --get user.email` 确认一下再提交。

同一类还要注意但更隐蔽的：文档里的示例路径。写成自己机器的真实路径
（`/Users/<你的用户名>/...` 或 `C:\Users\<用户名>\...`），就把本机用户名连
操作系统一起交代了。示例一律写 `/path/to/...`。这几条 `_selftest.js` 都会拦。

### 有一类上传会被直接拦下来

**「服务端有 N 台机身、送来的这份却是空的」这种上传会把服务端清空**，所以它被直接拒绝
（409），提示你先拉一次对齐。拦下来而不是问一句，是因为「自动同步」那条路没有人可问。

真实触发场景：本机存储被系统清理了（见下面 iPhone 那两条硬规则），
或者你换了台新设备打开、随手记了一台机身 —— 那一下就会把服务端几十台冲掉，
而且不报任何错。

真想清空，走设置页的「清空全部数据」，那条路会明确问你要不要连服务端一起清。

### 两台设备同时开自动同步会互相覆盖

同步是**整库快照，后写的赢，没有合并**。不过自建这一条比早先那几条好一些：
上传会带上「我上次读到的版本号」，对不上服务端就回 409 让客户端先拉一次，
所以「悄悄覆盖」变成了「被拦下并告诉你」。

真要两台一起用，建议只在一台上开自动同步，另一台手动对齐。

## 镜像怎么构建、怎么更新

这个仓库的产物是一个容器镜像，不是网页。

```
push 到 main / 打 v* 标签
        │
   GitHub Actions（.github/workflows/docker.yml）
        │  ① node _selftest.js         ← 不过就不构建
        │  ② 构建 linux/amd64
        │  ③ 拿真镜像起一个容器，走一遍
        │     探活 → 设密码 → 登录 → 存 → 读
        │  ④ 推 docker.io/liritian/film-tap
        │
   Docker Hub（公开镜像仓库）
        │
   NAS 上的 watchtower（每小时查一次）
        │  有新镜像 → 重建 film-tap 容器
        │
   完事。数据在 data 卷里，换容器不动它，也不用重新登录。
```

**推的是 Docker Hub，不是 GHCR。** 理由只有一个字：拉得到。`ghcr.io` 在国内
经常拉不动，而 watchtower 是无人值守的 —— 拉不到它不会报错，只会一直停在旧镜像上，
看起来「自动更新配好了」其实从没成功过。Docker Hub 至少还能配镜像加速。

推之前要先在仓库里放两个 secret（**Settings → Secrets and variables → Actions**）：

| Secret | 从哪来 |
|---|---|
| `DOCKERHUB_USERNAME` | 你的 Docker Hub 用户名 |
| `DOCKERHUB_TOKEN` | Docker Hub → Account settings → Personal access tokens，权限给 Read & Write |

少任何一个，CI 会在登录那一步失败 —— 这是好事：宁可没有新镜像，也不要一个推不上去、
NAS 又拉不到的空欢喜。`.github/workflows/docker.yml` 顶部的注释里也写了这两条。

三道门是有意排成这个顺序的：

- **① 在构建之前跑自检。** 这是唯一能发现「改了 `index.html` 却忘了同步 `sw.js`
  里的 `SHELL_FP`」的地方。那个疏漏的后果是线上是新版、手机上永远停在旧版，
  而且**不报任何错** —— 自动化更新之后更没人盯着。
- **③ 构建之后再验一次真镜像。** 光看「构建成功」证明不了镜像能用：`COPY` 漏了文件、
  `.dockerignore` 手滑把 `server.py` 挡掉，都会构建成功但起不来。所以真的起一个容器，
  设密码、登录、写一份数据、读回来、再确认未登录读不到数据。
- **② 自检不过就不 push。** 宁可没有新镜像，也不要一个坏镜像被 watchtower 自动装上。

标签：`latest` 跟着 main，`sha-<短哈希>` 每个提交一个，打 `v1.2.3` 这样的 tag 就有同名标签。
想固定版本就把 `IMAGE` 指到具体标签，别用 `latest`。

### 部署

```bash
NAS_HOST=<你的 NAS 地址> NAS_USER=<SSH 用户> SSH_PORT=<SSH 端口> ./nas/deploy.sh
```

脚本做的事：拉镜像 → 建 `<部署根>/data` → 起容器（**只挂 data 卷**）→
可选地设一次密码 → 起 watchtower。默认 `<部署根>` 是 `/vol1/@appdata/film-tap`、
端口 `8300`。**地址、端口、密码一律从环境变量进来，脚本里一个都不写死** ——
它会出现在公开仓库里，`_selftest.js` 的凭据护栏也扫它。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `NAS_HOST` | 必填 | NAS 地址 |
| `NAS_USER` / `SSH_PORT` | 当前用户 / 22 | SSH |
| `BASE` | `/vol1/@appdata/film-tap` | 部署根，只用来放 `data/` |
| `PORT` | `8300` | 对外端口（容器内部固定 8300，这里只映射） |
| `UID_GID` | `1000:1001` | 容器以哪个身份跑，让数据文件归你而不是 root |
| `IMAGE` | `docker.io/liritian/film-tap:latest` | 换标签就能固定版本 |
| `FT_PASSWORD` | 空 | 只在首次初始化密码时用 |
| `WATCHTOWER` | `yes` | 设 `no` 就不装自动更新 |

首次设一次密码（以后改密码是同一条命令）：

```bash
ssh -p <SSH 端口> -t <SSH 用户>@<你的 NAS 地址> \
  'docker exec -it film-tap python3 /app/server.py --set-password'
```

反代那边加一条：域名 → `http://127.0.0.1:8300`。用 Lucky 的话，
在现有那条 Web 服务规则下再挂一条子规则就行（按域名分流，TLS 复用同一张泛域名证书）。

想立刻更新一次、不等 watchtower 那个轮询间隔：

```bash
NAS_HOST=<你的 NAS 地址> ./nas/update.sh
```

它只是让 watchtower 跑一遍 `--run-once`，所以**就算部署时用了 `WATCHTOWER=no`** 也能用 ——
那是一次性容器，跑完就退，不需要把 docker socket 交给一个常驻容器。

> ⚠️ **watchtower 要挂 `/var/run/docker.sock`，这等于把 NAS 的 Docker 控制权
> 交给这个容器。** 脚本用 `--label-enable` 把它限制在「打了
> `com.centurylinklabs.watchtower.enable` 标签的容器」上，所以它**不会**去重建
> NAS 上别的容器。但如果你不想要这条通道，就把 `WATCHTOWER=no`，
> 改用 `nas/update.sh` 手动更新。
>
> 另外 `containrrr/watchtower` 这个老牌镜像在 2025-12 已经被作者归档（不再修安全漏洞），
> 脚本用的是维护中的社区分支 `nickfedor/watchtower`。两者配置完全兼容。
>
> 还有一点值得知道：自动更新意味着**升级时机不由你决定**。数据和配置都在
> `data` 卷里，容器换掉不动它们，所以回滚就是换个标签再起一次
> （`IMAGE=docker.io/liritian/film-tap:sha-xxxxxxx`）。

### 几个刻意的设计

- **代码在镜像里，不挂 app 卷。** 挂卷的话「更新」= 往 NAS 上传新文件，
  于是 NAS 上的代码和仓库里的代码会各自漂移，出问题时第一件要确认的事
  变成「NAS 上那份到底是哪一版」。打进镜像之后，镜像标签就是版本。
- **容器端口只绑 `127.0.0.1`，不绑 `0.0.0.0`。** 后端因此根本不进局域网 ——
  局域网上任何一台设备都打不到它，只有反代（跑在 NAS 本机）连得上。
- **密码只以加盐哈希（PBKDF2-SHA256，20 万次）落在 `config.json`（0600）**，
  页面里、代码里、日志里都不出现明文。日志只记「方法 + 路径 + 状态码」，**绝不记请求体**。
- **写文件是「同目录临时文件 → fsync → `os.replace`」**，半截写入不会顶掉好的那份。
- **带版本号上传。** 客户端把「上次读到的内容哈希」一起发过去，对不上就回 409，
  让它先拉一次。
- **密码错必须说成「密码不对」**，不能和「连不上」混成一句 ——
  混了的话用户会去查一个根本没坏的网络。这个项目就是从这类误判里长出来的。

> 用 Lucky 的话有一个实测结论：**它的反代不转发任何协议头**
> （`X-Forwarded-Proto` / `X-Forwarded-Ssl` / `Forwarded` 一个都没有），
> 所以后端光看请求分辨不出外面是不是 https。镜像里 `FT_ASSUME_HTTPS=1` 是默认值，
> 会话 cookie 因此会带上 `Secure`。要验证，`/api/health` 会把这个判断结果报出来
> （`https` 字段）。如果哪天改成不起 TLS 直连调试，用 `--no-assume-https` 关掉它。

### 它没有解决什么

- **可用性取决于你家的网络。** 这条依赖你家的 IPv6（或任何能让外面连进来的方式）。
  没有 IPv6 的网络打不开 —— 这是自建唯一的实质代价。
- **「页面公开」不会因为换个地方放就自己变好。** 域名是公网可解析的，
  知道子域名的人就能打开这个页面。所以真正要护住的是**数据**：`/api/*` 一律要会话，
  没登录只有 401。页面本身不含你的任何数据，拿到了也只是同一个空壳。
- **标签网址会带上端口**（`https://<域名>:<端口>/?c=m6`）—— 反代没有占用 443，
  所以端口写在了 URL 里。能用，但换端口就得重写标签，这一点心里有数。
- **更新是自动的，回滚是手动的。** 没有「自动发现问题就回退」这种东西。

### WebDAV 那条路（默认不开）

留着是给「页面不在 NAS 上、但手里有别的 WebDAV」那种情况的。它有三个前提，
缺一个就连不上，**而且三种失败长得一模一样，都像「NAS 没开机」**：

1. **WebDAV 地址必须是 `https://`，而且证书要被浏览器认可。** 浏览器不允许
   https 页面发出 http 请求（混合内容）；自签证书则在 TLS 阶段就被拒。
   两种都拦得很彻底 —— 请求根本不会离开浏览器。
2. **NAS 的 WebDAV 必须允许跨域（CORS）。** 请求是从这个站点发往 WebDAV 的，
   属于跨域；带 `Authorization` 头又会触发预检（`OPTIONS`）。服务器得回
   `Access-Control-Allow-Origin`，并在预检里放行 `Authorization`、`Content-Type`。
3. **得有人来满足上面两条 —— 而 NAS 自带的 WebDAV 通常两条都不满足。**
   群晖自带的预检会卡到超时；飞牛（fnOS）自带的是自签证书，
   而且**不提供任何 CORS 设置项**。所以「换个地址再试」是没用的。

设置页有「**测试连接**」：它先用一次不带凭据、不读响应的探测（`mode:"no-cors"`）
确认连接能不能建起来（这一层同时兜住证书），再发正常请求。于是能分开说清是
**网络/证书不通 · 密码不对 · 被跨域拦了**，而不是笼统一句「连不上」。

凭据只保存在本机 `localStorage`（键 `filmtap.webdav`），不进代码、也不随页面发布出去。

## 怎么用

只有一个地址：

```
https://film.792420124.xyz:16666/?c=<机身ID>
```

第一次打开会让你设密码（在 NAS 上跑一次 `--set-password`），之后这台设备就记住了。

本地预览：

```bash
python -m http.server 8080
```

> 直接双击 `index.html` 只能看界面 —— `file://` 下 Service Worker 不注册、离线缓存失效，
> 标签网址会算成 `file:///C:/...`，而且设置页的 NAS 那一栏会正确地收起
> （因为它探不到 `/api/health`，那正是「不是从后端打开的」这个答案本身）。

打开后点「载入示例数据」可以先看看成品长什么样。

### 更新之后手机上还是旧界面？

Service Worker 是缓存优先，浏览器靠 **`sw.js` 的字节变化**判断要不要装新 SW。
镜像更新是后台发生的，所以：**刷新一次**让浏览器拿到新的 `sw.js`，
新 SW 的 `activate` 会删掉旧 cache，再**刷新第二次**就是新版了。
如果一直不对，去设置 → Safari 里清一下这个站点的网站数据（会连 `localStorage` 一起清，
但数据在 NAS 上，重新输一次密码就全回来了 —— 这正是自建那条路的价值）。

## iPhone 上的两条硬规则

这个 App 在 iPhone 上有两个绕不过去的行为，直接决定该怎么用。

> 下面这两条**只对 iPhone 成立**。Android 上把 PWA 装到桌面反而是加分项：
> 独立窗口、不受「闲置清理」那类策略影响，而且碰标签的行为也更可控。
> 换句话说，「别装到主屏」是 iOS 的存储隔离逼出来的规矩，不是这个 App 的偏好。

### 1. 碰标签只会打开 Safari，不会打开主屏 Web App

iOS 的后台读卡，只在标签里是**有效的 Apple Universal Link** 时才会把链接交给 App ——
那需要原生 App 用 Associated Domains 声明域名，并在站点上放
`apple-app-site-association`。我们是纯网页，没有原生 App，
所以 iOS 只当它是普通网址，**一律交给 Safari 打开**。

推论：**不要「添加到主屏幕」。** 装了不会更顺，反而会在手机上多出第二个数据库 ——
主屏 Web App 的存储与 Safari 是**互相隔离**的（iOS 把每次安装当成一个独立 origin）。
碰标签进去的是 Safari 那份，点主屏图标进去的是空的。

> 反过来说，正因为数据在 NAS 上，「哪一份 localStorage」不再那么要命 ——
> 换个容器打开，输一次密码数据就回来了。但仍然不建议装：多一个容器就多一件事要解释。

### 2. Safari 里的数据闲置 7 天会被静默清空

Safari 的 ITP 会清掉「7 天内没有任何交互」的 origin 的全部**脚本可写**存储
（localStorage / IndexedDB / Cache API / `document.cookie`），没有报错、没有提示，
下次打开就是空库。装了主屏 App 的 origin 豁免这条，但按上一条我们不用主屏 App。

偏偏这个 App 的全部价值就是「记住机身里装的什么卷」，正是最怕被清的那类数据。
四层防护，从最省心往下排：

- **跑在自建后端上（就是现在这个形态）—— 这一层不需要任何对策。**
  登录态是服务器下发的 cookie（还带 `HttpOnly`），不在这轮清理范围内，
  所以本机被清之后打开页面就自己把数据拉回来了。
- **顺手「导出备份（JSON）」存进 iCloud Drive。** 设置页也有「导入备份」，
  两个容器之间、两台手机之间都靠它搬。**它不依赖任何凭据和服务，是真正保命的那条路。**
- **配 WebDAV 备份** —— 万一被清，重填地址账号再点「从 NAS 恢复」。
  它的凭据是你自己设的、**你能记住**。⚠️ 前提是那三个前提都满足（见上一节），
  否则这个地址根本发不出请求。
- 哪怕什么都不配，**每周打开一次**也能重置计时器（碰任意一个标签即算一次交互）。
  注意「7 天」是从**最后一次交互**算起，不是从配好那天算。

## 一次性的准备（每台机身做一次）

推荐「先写卡，再碰一下登记」——这样机身 ID 由你自己定，好记也好念：

1. **挑一个短 ID** —— 小写字母数字，别重复：`m6` / `fm2` / `rollei35`
2. **写标签** —— 用 NFC Tools 写入一条 **URL** 记录：
   `https://film.792420124.xyz:16666/?c=m6`
   必须是 URI 记录且放**第一条**：iOS 后台读取只认 URI 记录，多条时只用第一条，
   也不支持自定义 scheme（`film://` 这种写了也读不到）
3. **碰一下登记** —— 系统弹出通知 → 点开 → 页面显示「这个挂件还没登记」，
   填名称、品牌、型号、画幅 → 保存。以后碰这一下就直接落到这台机身
4. **打印挂件** —— `python model/build_fob.py` 出 `fob.stl`，层高 0.16mm，
   打完**第 17 层**（Z = 2.72mm）暂停放入标签，再封顶 2.24mm

> 机身 ID 也可以让 App 生成：首页「＋ 添加机身」会分配一个 `cam-xxxxx`，
> 再去 `#/settings` 复制完整标签 URL 写卡。两种都行，只是 `m6` 这种自己起的更好认。

标签只写这一次，之后换卷全在 App 里改。

## 日常

碰一下 → 直接落在那台机身：

- **换一卷** —— 选型号，张数按画幅预填（135 → 36，120 → 12）；回卷自动归档进「拍过的卷」
- **编辑这卷** —— 填 ISO 与实拍 EI，会自动给出推拉档位提示
- **复制冲扫备注** —— 一键生成能直接发给店家的说明（型号、EI、推拉、装卷日期）
- **库存自动扣** —— 有库存的前提下，这一卷装完就从 `#/films` 里减一卷
- 装得久了页面会标「偏久」，超过 180 天提示该冲了

这一页没有「过片 ＋1」是有意的。胶片机的计数器就在机身上，一低头就能看见；
在手机里再点一遍等于把同一个数字维护两次，而错误只会出现在更麻烦的那一次。
所以「换一卷」是这一页的主按钮 —— 它是这里唯一真正改变状态的动作。

## 胶卷库存

`#/films`。记的不是「机身里装的什么卷」（那是装卷记录的事），而是**柜子里还剩什么**。

一条库存记七个字段：型号、画幅、还有几卷、有效期、购入日期、单价、备注。
列表按**最快到期的排最前**，并给「已过期 / 本月到期 / 还剩 N 个月」的标签。

> **同一款卷在 135 和 120 上是两条库存。** 价格、张数都不一样，合成一条会算不清成本。
> 所以库存的唯一标识是「型号 + 画幅」，不是型号本身。
> 写型号时中文可以直接写（`富士 100`），不会被当成空值或跟别的款混淆。

装卷时会自动在这个库里**扣一卷**：装成功提示「库存还剩 N 卷」；
库里记的是 0 卷会提醒你对一下。编辑一条已存在的装卷记录**不会重复扣**。

### 从表格导入

`#/films/import`，三步：选文件 → 对列 → 确认。

表头**不用改**，认得出来就自动对：型号 / 数量 / 画幅 / 有效期 / 购入日期 / 单价 / 备注。
同义写法也认，例如型号那列写「胶卷型号」「品名」「film stock」都行，
数量写「存量」「剩余卷数」「rolls」，有效期写「到期」「保质期」「expiry」。
认不准的那一列会在第二步让你用下拉手工指定，**不靠猜**。

- 支持 **CSV / TSV / 直接用 Excel 粘贴**。制表符、分号、竖线分隔都能嗅探出来，
  字段里带逗号（`"Fuji, 分装"`）、带引号、带 BOM 都处理了。
  嗅探会看**前几行**而不是只看首行 —— 真实表格第一行经常是个跨列大标题，
  只看首行的话制表符文件会被判成逗号，整张表就废了。
- 中文 Windows 上 Excel 另存的 CSV 默认是 **GBK**，不是 UTF-8 —— 两种编码都能读。
- **`.xlsx` 读不了**（它是个压缩包，浏览器里解不了），请先在 Excel 里「另存为 CSV」。
- 「已有的同款怎么办」：**覆盖** = 这张表当权威全量，第一次整份导入用这个；
  **累加** = 这张表当新买的一批，跟现有存量相加。
- 文件只在这台设备上解析，不会上传到任何地方。

> 库存和机身一样是数据库的一个顶层字段，所以它自动获得上传、回灌、
> JSON 导出导入、NAS 同步 —— 同步层不认识业务字段，加了新字段不用改同步代码。

## 自检与截图

```bash
node _selftest.js      # 全部视图渲染 + 张数 / 装卷 / 库存与导入 / 改名迁移 / 凭据护栏
python _shots.py       # 需先起本地服务，截图输出到 shots/

# 后两个要 playwright，装在工程 venv 里，别直接敲 `python`
# （换成你自己的 venv 路径；下面这个只是个例子）
PY=/path/to/your/venv/bin/python
$PY _firstrun.py                        # 打线上那个部署，走一遍「空库首次使用」
$PY _firstrun.py http://127.0.0.1:8123  # 只打本地静态服务（NAS 那几条会自动跳过）
```

> `_selftest.js` 是在内存里造数据 + 直接跳哈希，从来不点按钮、不进表单、
> 不经过 Service Worker —— 于是「空库 → 登记第一台机身 → 装卷 → 刷新 → 数据还在」
> 这条**每个新用户唯一会走的**路径，在自检里是完全空白的。
> `_firstrun.py` 就是补这块：用真浏览器在线上页面点一遍。
>
> CI 里这三样跑的是前两样：`node _selftest.js` 当构建的前置门，
> 真镜像冒烟那一步等于把 `_firstrun.py` 的关键路径在容器里重跑一遍。

自检还钉住了这些容易悄悄坏掉的性质：

- **机身 ID 不能逃出 `onclick`**。ID 从 URL 的 `?c=` 来（就是 NFC 标签里的内容），
  又会被拼进 `onclick`。断言不是「字符串里有没有那几个字」——转义之后那几个字还在，
  那种断言两边都通过。做法是把渲染出的每个 `onclick` **真的喂给 JS 引擎跑一遍**，
  看它是不是只调了一次处理函数、有没有碰到 `document`。
  （设置页有四种排版：还没探到 / 不是从 NAS 打开 / 探到了没登录 / 已登录，每套都要各扫一遍。）
- **设置页不许再出现 GitHub 相关的字眼**。私有仓库那整套已经拆掉了，
  这条是防它偷偷长回来 —— 有残留就说明没摘干净。
- **读不出来的数据要留底**（`filmtap.v1.corrupt`），后面来的写入不能顶掉它。
- **删掉的功能要真的是删干净了**。删功能留下的往往不是报错，是半截残骸：
  某个入口没摘掉、某个视图还在算一个不会变的数、或者老数据里的字段还在被同步来同步去。
  所以这里正面断言「函数没了、页面里没有残留、表单里没有那个输入框」，
  以及**老库里的 `shots` 会在 `normalizeRoll` 里被清掉**（`total` 必须留下 ——
  那是「这卷多少张」，和「已拍几张」是两回事）。
- **历史里的坏记录只剔那一条**，不能让整页变白。
- **点「同步到 NAS」（WebDAV 那条）不触达自建后端** —— 断言落在
  「那个 PUT 去了哪个路径」上，不看返回值。
- **自建后端那条路的每一环**（要联网，所以和上面一样在异步段里用打桩的 fetch 跑）：
  探活认的是后端**自报的身份**（别的服务恰好也有 `/api/health` 时不能认错）；
  请求必须是同源相对路径并带 cookie（写死域名的话换个域名就断）；
  回灌只在**本机为空**时动手、本机有数据时一个请求都不发；
  上传要带版本号；两种 409 都要拦下并说明白；会话失效不刷屏；
  **清空本机存储后能自动恢复**；密码框空着点不动；密码绝不落盘。

> ⚠️ 加新的可点击元素时记住：往 `onclick` 里塞数据要过 `jsq()`（跳转走 `goAttr()` /
> `tapRow()`）。`esc()` 在这件事上不管用 —— 它把 `'` 变成 `&#39;`，
> HTML 解析器读属性时又会还原成 `'`，字符串照样被闭掉。
> `encodeURIComponent` 也不行，它不编码 `! ' ( ) *`。
> 还有一件事：加了新的 `onclick` **要把它挂的处理函数名补进 `_selftest.js` 的
> `PARAMS` 表**，否则那条扫描会报「有泄漏」—— 那个失败看着像注入，其实是表过期了。

`_selftest.js` 里有一道**凭据护栏**，扫描仓库里所有发得出去的文本文件。
关键认识是：**暴露面是「仓库可见范围」，不是「站点可访问范围」** ——
上次泄露就发生在这个自检文件里，那时候它不在站点上（Pages 会跳过下划线开头的文件），
但它在公开仓库里照样能拿到。所以新加的脚本、`Dockerfile`、工作流都要加进
`SHIPPED` 列表，没加进去就等于没护栏。出现内网网段、Basic 认证头、GitHub 令牌形状，
或把凭据直接写成常量赋值，自检直接失败。

> 护栏自己的样本也只在运行时拼接，绝不把真实值或可命中的形状写成字面量 ——
> 否则护栏本身就成了新的泄露点。这个坑踩过。

### 改完 `index.html` 必须同步改 `sw.js`

Service Worker 取文件是「缓存优先」，而浏览器只靠 **`sw.js` 的字节变化**
来判断要不要装新 SW。所以只改 `index.html` 不动 `sw.js`，线上是新版、
手机上却一直停在旧版界面，**而且不报任何错**。这个坑踩过。

现在由自检强制：`sw.js` 里存着 shell 文件（`index.html` + `manifest.webmanifest`）
的 SHA-256，自检会算一遍比对。对不上就失败，并把正确的值打出来让你照抄进
`sw.js` —— 那一行一改，`sw.js` 的字节就变了，浏览器才终于会去装新 SW。
所以改 `index.html` 之后的固定动作是：跑一次 `node _selftest.js`，
按提示更新 `SHELL_FP` 并把 `CACHE` 的版本号 +1。

CI 把这件事变成了硬门：自检不过就**不构建镜像**。自动更新之后这一条比以前更要紧 ——
更新是无人值守发生的，没人盯着「手机上是不是还是旧版」。

`_selftest.js` 的驱动整体是一个 `String.raw` 模板字符串 —— 里面写
`\n`、`\r`、`\d` 都不用再翻倍。改用 `String.raw` 之前，每写一个反斜杠
都得写两遍，漏一个就报「Invalid or unexpected token」还没行号。
（同理：驱动里**不能出现反引号**，会被当成模板串的结尾。）

## 硬件

挂件是 3D 打印的，中间留了 NTAG213 / 215 / 216 圆片标签的腔体：

## 历史

上一代是 `film-camera-tracker`（胶片管家）：纯手动索引、没有 NFC 概念。
这一版把它的统计页、机身结构化字段、NAS 同步吸收进来，换成 NFC 直达的架构重做。
（它的过片计数没有再收 —— 见上面「这里不数快门」。）

项目名统一成 `film-tap` 之前叫过 `film-nfc`，界面标题叫过「胶片簿」——
仓库名、目录名、界面名已经全部统一，不再是三个名字。

部署形态也换过两轮：最早是 GitHub Pages 上的纯静态页（数据只能塞进一个私有仓库，
再配一枚令牌）；中间加过自建后端；现在是**只有自建后端这一种形态**，
页面和数据都从 NAS 上那个容器发出来，GitHub 只剩下「自动构建镜像」这一个职责。
